# P3P3DS current execution state

This is the current source of truth, newest entries first. Since 2026-10-11 this fork targets Persona (ULUS-10432); every entry below the retarget section is upstream P3P3DS evidence about ULUS-10512 and does not describe Persona; each section says whether it was measured on the PC runner, in Azahar or on a real New 3DS.

## Display lists run on the GE worker (core 2) (2026-10-13)

- Maintainer chose this step (2026-10-13) after the breakdown below: about 16 us of the main core's 54 us per draw is GE command execution and the stall-update import.
- Change (`core/src/hle/ge.cpp`, `core/include/p3p3ds/hle/ge.hpp`, `core/src/ge/async_renderer.*`, `core/src/hle/fork_kernel.cpp`, `platform/3ds/main.cpp`, all `P3P3DS:`-marked): `GeManager::set_async_executor` makes the threaded renderer's worker run the display lists. On the game's thread `sceGeEnqueue`/`sceGeListUpdateStallAddr` only queue a task (`AsyncRenderer::post_task`: no heap allocation per update; the enqueue carries one `GeListInfo`); the worker adds lists, applies stall addresses and pumps, drawing through its own renderer directly (no State/Draw records). Commands that must run on the game's thread stop the worker at that command (`worker_needs_main`: list completion and its finish callback, SIGNAL, the first PRIM's event, anything that would stop the runtime, census and draw log); the game's thread runs that one command before its next import (`fork_kernel.cpp` pre-import hook) or at `sceGeDrawSync`/`sceGeListSync`/`sceGeGetCmd`/`sceGeGetMtx` (`quiesce`: drain, then the leftover), then the worker continues. The list table, registers and queue are touched by the game's thread only while the worker is idle. With lists on the worker the stall override skips its census and batching. The 3DS runner turns it on when the GE worker runs on core 2 (report `cores: ..., lists on core2`); an empty `sdmc:/persona3ds/ge_sync.txt` keeps lists on the game's core. The report's `ge in: draw` now counts the renderer's draws (both paths). [INFERRED] deviation: a stall update for a list the worker already completed returns 0 instead of `already` (0x80000020).
- [VERIFIED] host tests (CTest 29/29): `test_fork_kernel` `test_ge_async_execution`: 400 stall updates of random lists (registers, matrices, LOADCLUT, CALL/RET, JUMP over a word that would stop the runtime, SIGNAL+END, FINISH+END), `sceGeGetCmd` mid-list, a second list, `sceGeDrawSync`: the renderer sees identical calls, registers, matrices and CLUT on the game's thread (direct and queued) and on the worker, with the census off (3DS) and on (every PRIM handed to the game's thread); same `sceGeGetCmd` values and sync result. With the worker's draws dropped it fails; with the worker ignoring stall updates it fails. ThreadSanitizer build of `test_fork_kernel` (`.cache/tsan`, linked without `-static`): no reports in 3 runs, after one fix (the stall override read the list table on the game's thread).
- [VERIFIED] host benchmark (`.tmp/gebench`, census off as on the 3DS, null renderer, 20,000 updates of the dungeon pattern): game's thread 0.27-0.36 us per update with lists on it, 0.07-0.10 us with lists on the worker (worker started after the loop), worker 0.21-0.47 us per update; x86 host with 2 vCPUs, noisy.
- [UNVERIFIED] on the New 3DS: main-core `hle` share well below 29 % in the school dungeon and more draws per second, until core 2 (`gpu thd: busy`) saturates; no change in what is drawn. Risks to watch: hangs at `sceGeDrawSync`, missing or late frames, crashes when entering/leaving menus or movies.

- [VERIFIED] cost being removed, by the code (`core/src/ge/async_renderer.cpp` before this change): every State record copied all of `GeRegisters` but the CLUT (1,624 bytes) into a stack `StatePayload`, then into the ring (record 1,632 bytes), and the worker copied it out twice more. The worker applies the pairs. CLUT records are unchanged. ## Dungeon: LOADCLUT was the cost (40 us per stall update); fast path (2026-10-11)

- [VERIFIED] Maintainer's New 3DS on `49877806` (label `595ea75e`), school dungeon, last 10 s: 43 % of real time, `stall: 10.0k/s, GE work 56.3 us per update`, `stall split: draw 9.5 sync 0.8 rest 46.1 us`, **`op cost: C4:40.2 04:11.3 01:0.5 1E:0.5 12:0.5 10:0.4 us/update`**: LOADCLUT costs 40.2 us per stall update, PRIM (with the renderer hand-over) 11.3 us, every other opcode under 1 us. [WRONG] the conclusion of the opcode census (`c273dadd`) that LOADCLUT is not among the frequent commands: the census reads only the list's own words and does not follow CALLs, and the palette loads are in the called sub-lists. CLUT copies to the GE worker (palette actually changed) are about 0.3 per update, so most loads reload the same palette.
- Cause (`core/src/hle/ge.cpp` `execute`, case 0xC4): per palette word (up to 256) an out-of-line `GuestMemory::contains`, then `load32` (which calls `resolve` -> `contains` again), then a 64-bit-multiply hash step. [VERIFIED] host benchmark (`.tmp/gebench/gebench.cpp`, now with CLUTADDR/CLUTADDRUPPER and a 1 KiB LOADCLUT per draw, the same palette every draw): callgrind 141,694,331 instructions for 2,000 stall updates (about 70,800 per update), 4.84 us per update on the x86 host.
- Fix (`P3P3DS:` patch in `ge.cpp`, under the maintainer's GE-path exception): a palette range inside guest memory is read with one `raw_pointer` lookup and `memcpy` (guest and host little-endian, `static_assert`), and a reload of the same number of words with the same bytes (`memcmp`) keeps the palette and its hash; a range not fully inside guest memory keeps the per-word path. [VERIFIED] host benchmark after: 11,751,992 instructions for 2,000 updates (about 5,900 per update, 12x fewer), 0.56 us per update. [VERIFIED] `test_ge_loadclut_fast_path` (CTest 29/29 with pspautotests): palette, word count and hash equal the original per-word algorithm for a full random palette, the same bytes again, one word changed, 16 words after 256, a shifted source, a range running past the end of RAM (fallback), a VRAM palette (twice), zero blocks (twice) and a request above 1 KiB; mutations (skip without the word-count condition; a copy 4 bytes short) fail it.
- [UNVERIFIED] on the New 3DS: expected `op cost` C4 at a few us and GE work per update about 15 us (was 56), the main core's `hle` share far lower, and the dungeon much closer to its 30 fps target. Applies to every scene that loads palettes per draw (battles, menus), not only dungeons.

## Dungeon: 44 us per stall update outside draw/sync; batched stall updates (2026-10-11)

- [VERIFIED] Maintainer's New 3DS on `4d40f9ba` (label `595ea75e`), school dungeon, last 10 s: 44 % of real time, `stall: 9.9k/s, GE work 54.4 us per call`, `stall split: draw 9.6 sync 0.8 rest 44.1 us`, `stall ops` as before (one each of TEXFLUSH, VADDR, BASE, PRIM, VTYPE, texture enable, TEXADDR0), `ge in: cmd 156.4k draw 9.9k` (about 16 commands per update). The renderer calls are about 10 us; about 44 us per update is spent in `update_stall` / `pump` / `execute` on about 16 commands whose code paths are register writes, a bounds check (`GuestMemory::contains`) and a map lookup; diagnostic events are compiled out (`Runtime::frontier_diagnostics` is `constexpr false` in the production build). [INFERRED] the GE path runs cold: between two of the 10,000 updates per second the game runs its own recompiled code (40-44 MB of ARM code), which evicts the GE code and data from the ARM11's 16 KiB L1 caches, so each update pays cache misses to FCRAM; the same fits `sceKernelReferEventFlagStatus` at about 11.7 us per call. Not measured directly; the batching below tests it (per-update GE work should fall well below 54 us if it holds).
- Change: sceGeListUpdateStallAddr batching (`core/src/hle/fork_kernel.cpp`, fork-owned; `set_ge_stall_batching`). A valid update (known list, not completed, aligned address) only records the new stall address and returns 0 (what `update_stall` returns for it); upstream's `update_stall` runs the recorded update when 32 are pending, when another list is updated, before any other HLE import (new pre-import hook, `P3P3DS:` minimal patch in `recomp/PSPRecomp`: `set_runtime_pre_import_hook`, called inside the import's profiling scope right before its handler, in both `invoke_import` and `invoke_import_cached`), and before the frame is shown (`on_vblank` in `platform/3ds/main.cpp`). An update that cannot be deferred runs the pending one first, then itself, as upstream. Every import therefore sees the GE as if each update had run at once; only updates with nothing but game code between them run together. [INFERRED] no new memory-ordering risk: the async renderer already reads vertex memory on core 2 after the game has continued. GE finish callbacks run in an isolated context with their own stack (`GeManager::deliver_finish_callback`), so running them from the pre-import hook leaves the importing thread's context untouched; the pending state is cleared before running so imports made by a callback do not re-enter. A thread spinning on a GE flag without any import would wait for the next update or vblank; such a loop already hangs in this runtime (virtual time only advances at imports).
